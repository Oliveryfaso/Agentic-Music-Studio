## Must fix

1. **经典谱导入在两个提交之间会留下空项目** — **Important / P1**

   **位置：** `services/api/src/motif_forge/application/classical_import.py:88–91`（新增代码）。相关提交语义见 `application/projects.py` 的 `CreateProject.__call__`，以及 `infrastructure/persistence/database.py:88–100` 的 `PostgresTransaction.__aexit__`。

   **What this is:** `CreateClassicalScore` 先 await `CreateProject(...)`，它在自己的事务内写入并提交 Project、空 v1 root、main Branch 和 `project.create.v1` 幂等记录。返回后才打开第二事务，写原谱 Revision、工作分支和 `score-import.v1` 结果。

   **Problem / 触发：** API 进程在第一事务提交后、第二事务开始前退出，或第二事务报错回滚时，请求尚未成功但空 Project 已永久可见。没有原谱、工作分支或导入 receipt。用户刷新 Home 后新的 `ClassicalScoreEntry` 丢失仅保存在 `useRef` 的请求 key；重新点击导入产生另一 Project，旧空 Project 留在列表中。若继续操作这个空 Project，其 head 改变后原 key 的导入还会在第 104 行持续返回冲突。这是本轮明确要求的原子导入/重启恢复边界。

   **独立复现：** 在现有 FakeTransaction 的第二次 `__aenter__` 前注入停止（第一事务正常退出），不启动数据库或音频服务。结果为 `successful_transaction_exits=1 / projects=1 / branches=1 / revisions=1 / score_revisions=0 / import_receipts=0`；使用刷新后新 key 重试得到 `projects=2 / score_revisions=1`。原始输出：`research/p2-review-atomic-repro.json`。这是应用控制流复现；PostgreSQL 第一事务会真实提交的依据是实际 `PostgresTransaction.__aexit__` 的 commit 代码，本审查没有把内存复现表述成新 PG 运行证据。

   **Fix:** 将新建 Project/root、原谱 Revision、原分支 head、工作分支/active 指针、audit 和最终导入幂等记录放入同一外层事务。复用或提取 `CreateProject` 的事务内创建函数即可，无需新恢复平台；不要依靠事后删除空 Project 的补偿。增加一个在后半段写入失败时全量回滚的代表性测试，并验证成功请求的相同 key 仍重放同一结果。

   **If we skip it:** 导入失败/重启会留下与用户选择的经典谱不符的可见空作品；浏览器刷新重试不能自动恢复原操作，并会累积重复作品。该项影响当前导入路径的事务和恢复合同，需在正常推送前关闭。
